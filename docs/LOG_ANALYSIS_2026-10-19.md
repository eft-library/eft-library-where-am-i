# 실제 로그 기반 개발 가능 범위 분석

분석일: 2026-10-19. 대상: `log/`의 5개 실행 폴더, 45개 `.log` 파일(56,595,964바이트). 외부 자료가 아닌 제공된 로그와 현재 파서·감시 코드의 비교 결과다. 앱 코드는 변경하지 않았으며 Windows 실행·서버 연동 검증은 수행하지 않았다.

## 결론

Customs·Woods·Shoreline부터 맵 감지·레이드 시작·활동 이력을 개발한다. 좌표는 기존 스크린샷을 사용한다. output의 GameTimer로 타이머 기준을 수집하고 서버·웹에서 잔여 시간과 Woods BTR 예상 운행을 계산한다.

Woods는 타이머 확보·검증 대상이다. Customs·Shoreline은 타이머가 없어도 정상 동작하도록 한다. 실제 BTR 정차 이벤트, 로그 좌표 추적, 정확한 종료 감지와 실제 트랜짓 연결은 이번 개발 범위에서 제외한다. 현재 코드에는 output 수집·타이머 전송이 없어 추가 구현이 필요하다.

## 현재 코드와 구현 순서

현재 별칭과 정규식은 샘플의 `bigmap`, `woods`, `shoreline` 및 `GameStarted` 형식과 맞는다. 다만 이 판단은 코드·텍스트 비교이며 C# 실행 테스트 결과는 아니다. 전체 파일을 한 번 파싱하면 마지막 상태만 반환하므로 과거 6개 시작 이벤트를 모두 재생하지는 않는다.

1. 개인정보를 제거한 application·output 조각을 만들고 시간순 추가 방식으로 재생한다.
2. 같은 실행 폴더의 맵·시작·GameTimer를 레이드별로 연결하고 새 레이드에서는 이전 타이머를 초기화한다.
3. output 증분 읽기와 상태 보관을 구현하고 앱을 레이드 도중 실행한 경우도 검증한다.
4. 맵·시작·타이머 전송 계약을 서버와 합의하고 Woods 게임 화면과 웹 잔여 시간을 비교한다.
5. Customs·Shoreline의 타이머 누락, Woods 타이머 미확보 시 수동 입력 유지, 기존 스크린샷 위치 전달을 검증한다.

같은 맵 재입장, Customs → Woods, 파일 교체, 전송 지연·실패에서도 이전 맵·타이머가 섞이지 않아야 한다. 실제 트랜짓·정확한 종료·BTR 자체 이벤트 샘플 확보는 이번 개발의 선행 조건이 아니다.

## 실제 레이드 타이머 근거

6개 GameStarted에 대응하는 GameTimer 기록 6개가 있으며, Customs 4회와 Woods 1회는 35분, Shoreline 1회는 45분이다.

10.19 08:22:41 실행 폴더의 output_000.log:

- 140419행, Customs: `utcNow:10/18/2026 23:25:20 start:10/18/2026 23:25:20 escape:10/19/2026 00:00:20 PastTime:00:00:00`
- 426722행, Woods: `utcNow:10/18/2026 23:40:32 start:10/18/2026 23:40:32 escape:10/19/2026 00:15:32 PastTime:00:00:00`

`escape - utcNow`로 기록 당시 잔여 시간을 계산할 수 있다. 내부 시각은 utcNow라는 이름과 로컬 행 시각 대비 약 9시간 차이로 UTC로 해석할 근거가 있지만, 행 시각과 내부 시각에는 초 단위 차이도 있어 실제 게임 화면과 동기화 검증은 필요하다. 모든 샘플의 PastTime은 0이며 늦은 입장 상황은 미검증이다.

사용자 확정 범위에 맞춰 실제 트랜짓 연결·정확한 종료 감지는 우선 제외하고, 좌표는 기존 스크린샷을 사용한다. BTR 실제 정차 이벤트를 수집할 필요 없이 현재 맵과 타이머 기준을 서버·웹으로 전달하여 예상 운행을 표시하는 방향이다. 현재 감시기는 application만 읽으므로 output을 추가로 읽고 같은 실행 폴더의 맵·타이머를 연결해야 한다. output은 크므로 시작 기록이 뒤로 밀려도 유지되도록 증분 읽기와 상태 보관이 필요하다. 기존 레이드 API에는 타이머 필드가 없어 서버 계약 확장이 필요하다.

샘플의 Customs·Shoreline 타이머 존재는 보장 조건이 아니다. Woods 타이머가 없을 때도 임의의 35분을 적용하지 않고 수동 입력을 유지한다. 타이머 API 필드명과 자동 적용은 제안·구현 예정이며 현재 동작으로 소개하지 않는다.
