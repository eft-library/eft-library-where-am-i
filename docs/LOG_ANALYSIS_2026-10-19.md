# 실제 로그 기반 개발 가능 범위 분석

분석일: 2026-10-19. 대상: `log/`의 5개 실행 폴더, 45개 `.log` 파일(56,595,964바이트). 외부 자료가 아닌 제공된 로그와 현재 파서·감시 코드의 비교 결과다. 앱 코드는 변경하지 않았으며 Windows 실행·서버 연동 검증은 수행하지 않았다.

## 결론

Customs·Woods·Shoreline부터 맵 감지·레이드 시작·활동 이력을 개발한다. 좌표는 기존 스크린샷을 사용한다. output의 GameTimer로 타이머 기준을 수집하고 서버·웹에서 잔여 시간과 Woods BTR 예상 운행을 계산한다.

Woods는 타이머 확보·검증 대상이다. Customs·Shoreline은 타이머가 없어도 정상 동작하도록 한다. 실제 BTR 정차 이벤트, 로그 좌표 추적, 정확한 종료 감지와 실제 트랜짓 연결은 이번 개발 범위에서 제외한다. 현재 output 수집·레이드 연결·화면 확보 상태 표시까지 구현했다. 클라이언트의 타이머 포함 요청 전송도 구현했으며 백엔드·웹 반영은 [별도 API 요구사항](BACKEND_API_REQUIREMENTS.md)에 따라 후속 구현한다.

## 현재 코드와 구현 순서

1단계 완료: [로그 검증 자료와 재생 안내](../tests/fixtures/raid-logs/README.md)에 세 맵·같은 맵 재입장·Customs → Woods·타이머 누락 시나리오를 준비했다. Python 재생·자료 검증 3개 테스트가 통과했다. 당시에는 C#·WPF 실행 검증을 수행하지 않았으며 이후 진행 상태는 아래와 같다.

2단계 구현: `RaidSession`·`RaidTimer`와 `TarkovRaidSessionTracker`를 추가했다. 같은 실행의 맵·시작·타이머를 로그 시각순으로 연결하고 새 로딩에서 이전 시작·타이머를 초기화한다. 실제 C# 소스를 사용하는 별도 검증 프로젝트의 107개 검증과 Python 테스트 3개가 통과했다. WPF 파일 감시기 연결·output 증분 읽기·서버 전송은 아직 구현하지 않았다.

현재 별칭과 정규식은 샘플의 `bigmap`, `woods`, `shoreline` 및 `GameStarted` 형식과 맞는다. 다만 이 판단은 코드·텍스트 비교이며 C# 실행 테스트 결과는 아니다. 전체 파일을 한 번 파싱하면 마지막 상태만 반환하므로 과거 6개 시작 이벤트를 모두 재생하지는 않는다.

1. 개인정보를 제거한 application·output 조각을 만들고 시간순 추가 방식으로 재생한다.
2. 같은 실행 폴더의 맵·시작·GameTimer를 레이드별로 연결하고 새 레이드에서는 이전 타이머를 초기화한다.
3. output 증분 읽기와 상태 보관을 구현하고 앱을 레이드 도중 실행한 경우도 검증한다.
4. 맵·시작·타이머 전송 계약을 서버와 합의하고 Woods 게임 화면과 웹 잔여 시간을 비교한다.
5. Customs·Shoreline의 타이머 누락, Woods 타이머 미확보 시 수동 입력 유지, 기존 스크린샷 위치 전달을 검증한다.

같은 맵 재입장, Customs → Woods, 파일 교체, 전송 지연·실패에서도 이전 맵·타이머가 섞이지 않아야 한다. 실제 트랜짓·정확한 종료·BTR 자체 이벤트 샘플 확보는 이번 개발의 선행 조건이 아니다.

## 실제 레이드 타이머 근거

6개 GameStarted에 대응하는 GameTimer 기록 6개가 있으며, Customs 4회와 Woods 1회는 35분, Shoreline 1회는 45분이다.

10.19 08:22:41 실행 폴더의 output_000.log:

- 140419행, Customs: `utcNow:10/18/2026 23:25:20 start:10/18/2026 23:25:20 escape:10/19/2026 00:00:20 PastTime:00:00:00`
- 426722행, Woods: `utcNow:10/18/2026 23:40:32 start:10/18/2026 23:40:32 escape:10/19/2026 00:15:32 PastTime:00:00:00`

`escape - utcNow`로 기록 당시 잔여 시간을 계산할 수 있다. 내부 시각은 utcNow라는 이름과 로컬 행 시각 대비 약 9시간 차이로 UTC로 해석할 근거가 있지만, 행 시각과 내부 시각에는 초 단위 차이도 있어 실제 게임 화면과 동기화 검증은 필요하다. 모든 샘플의 PastTime은 0이며 늦은 입장 상황은 미검증이다.

사용자 확정 범위에 맞춰 실제 트랜짓 연결·정확한 종료 감지는 우선 제외하고, 좌표는 기존 스크린샷을 사용한다. BTR 실제 정차 이벤트를 수집할 필요 없이 현재 맵과 타이머 기준을 서버·웹으로 전달하여 예상 운행을 표시하는 방향이다. 분석 당시 감시기는 application만 읽었으나 이후 output 증분 읽기·연결·타이머 포함 요청 전송을 구현했다. 백엔드 수신 모델·WebSocket 반영은 별도 요구사항으로 남겼다.

샘플의 Customs·Shoreline 타이머 존재는 보장 조건이 아니다. Woods 타이머가 없을 때도 임의의 35분을 적용하지 않고 수동 입력을 유지한다. 타이머 API 필드명과 자동 적용은 제안·구현 예정이며 현재 동작으로 소개하지 않는다.

## 3단계 구현: 증분 파일 감시 연결

`IncrementalLogReader`·`TarkovLogSessionReader`를 추가하고 감시기에 연결했다. 같은 실행 폴더의 application·output을 최초에는 처음부터, 이후에는 추가된 바이트부터 읽는다. 부분 행·UTF-8 조각, 64KiB 초과 행, 파일 잘림·교체·회전·삭제, 앱 중간 실행과 재탐색을 처리한다. 읽기 실패 후에는 형제 파일까지 다시 복구한다. 중지·종료된 읽기 결과는 게시하지 않는다.

현재 화면에는 타이머 확보 여부, 기록 당시 잔여 시간과 기준 시각을 표시한다. 3단계 당시에는 실시간 카운트다운·타이머 API 전송이 없었다. 이후 전송 구현은 아래 4단계를 참고한다. 기존 로그 좌표 자동 전송 연결은 제거하여 스크린샷만 위치 출처로 사용한다. 정확한 종료 감지·트랜짓 연결은 구현하지 않는다.

검증에는 output만 변경되는 상황, 500KB를 넘는 잡음 뒤의 상태 유지, 신규 실행 폴더로 이동과 application 미발견 시 초기화도 포함한다. C# 검증 130개와 Python 테스트 3개가 통과했다. Windows 대상 WPF 프로젝트의 교차 빌드도 경고·오류 없이 통과했으며 실제 Windows UI 실행·게임 화면 동기화는 별도 확인이 필요하다.

## 4단계 구현: 타이머 포함 요청 전송

`SendRaidStateRequest`·`RaidSessionSender`를 추가해 SessionChanged에서 기존 레이드 API로 전송한다. 새 필드는 session_id·timer_observed_at·raid_ends_at이며, 타이머 미확보·로딩 상태는 명시적 null이다. 타이머가 나중에 확보되면 맵·시작이 같아도 다시 보낸다.

요청을 직렬화하고 대기 중인 이전 값과 과거 결과를 버린다. 일시 장애는 총 3회까지 시도하며 감지 중지·종료로 진행 중 요청과 재시도도 취소한다. 재개 시 동일 스냅샷을 다시 전달한다. HTTP 성공과 data:true를 모두 검사한다.

인접 백엔드의 기존 모델·서비스·WebSocket·응답 형식을 읽어 확인했다. 사용자 요청에 따라 백엔드·웹은 수정하지 않았으며 [백엔드 API 요구사항](BACKEND_API_REQUIREMENTS.md)에 별도로 정리했다. 현재 구버전 서버는 타이머 필드를 무시할 수 있어 운영의 BTR 자동화 완료로 볼 수 없다. 검증은 가짜 HTTP 핸들러를 사용하며 운영 서버에 요청하지 않았다.

검증 결과: C# 180개 검사와 Python 테스트 3개 통과. Windows 대상 교차 빌드도 경고·오류 없이 통과했다. 실제 Windows UI 실행·백엔드 새 필드 수신·웹 적용은 미검증이다.

## 5단계 구현: 상태 화면과 최근 활동

화면을 레이드·타이머, 스크린샷 위치, 로그 수집, 최근 활동으로 나눴다. 감지 켜짐·중지를 표시하고, 감지한 현재 맵을 여는 버튼을 연결했다. 미확인 맵은 기존 Customs로 연다. 실제 로그 실행 폴더·스크린샷 경로는 접어서 확인할 수 있다. 창 크기 조절·전체 스크롤·버튼 줄바꿈을 적용했다.

`ActivityEntry`·`ActivityHistory`는 기록 시각·종류·오류 여부를 최신순으로 최대 100개 보관한다. 오류 필터를 제공하고 성공 이후에도 이전 실패를 확인할 수 있다. 앱 종료 시 이력은 사라지며 서버 전송·진단 복사·영구 저장은 추가하지 않았다.

스크린샷 저장 대기·전송 상태를 별도로 표시하고 잘못된 JSON 응답을 실패로 처리한다. 감지 순서가 뒤집힌 과거 결과는 최신 스크린샷 상태를 덮어쓰지 않고 이력에 남는다. 저장 대기 중 더 최신 스크린샷이 감지되면 이전 대기 파일의 신규 전송을 생략한다. 5단계 당시 전송 중인 스크린샷 요청의 취소·직렬화는 후속이었으며, 아래 6단계에서 구현했다.

이력 보관·복구 후 오류 유지·현재 맵 링크와 미확인 값 처리를 검증했다. C# 검증은 193개이며 Windows UI 실물·DPI·키보드·레이아웃은 별도 확인이 필요하다. 백엔드·웹은 이번에도 변경하지 않았다.

## 6단계 구현: 스크린샷 전송 안정화

`ScreenshotLocationSender`로 파일명 검사·3초 중복 억제·파일 준비·전송을 ViewModel에서 분리했다. `LatestJsonSender`를 추출하여 레이드와 스크린샷의 응답 확인·각 API별 직렬화·최신 대기값 유지·총 3회 이내 재시도·취소 정책을 공유한다. 기존 레이드 전송 검사도 같은 실제 코드를 통해 계속 수행한다.

스크린샷을 감지할 때 순번을 예약한다. 오래된 파일의 저장이 늦게 끝나거나 이전 요청의 재시도 대기 중 새 파일이 감지돼도 이전 위치가 뒤늦게 전송되지 않도록 한다. 길이가 0인 파일도 다음 확인을 시도하도록 보완했다. 이미지 데이터나 전체 경로는 전송하지 않고 기존 email·location 계약을 유지한다.

중지·종료 시 스크린샷 준비 대기·HTTP·재시도를 취소하며, 무효화한 진행 알림과 결과는 최신 화면에 반영하지 않는다. 재개 후에는 새 스크린샷부터 처리하고 과거 파일은 재전송하지 않는다. HTTP 시간 초과·취소 이후 서버가 처리하는 요청의 순서까지는 클라이언트만으로 보장할 수 없다.

실제 임시 파일과 가짜 HTTP 핸들러로 0바이트 파일의 지연 저장, 중복 이벤트, 저장 순서 역전, 전송 직렬화와 중간값 생략, 최신 감지에 따른 과거 재시도 중단, 실패 응답·재시도 제한, 파일 준비·HTTP·재시도 중 취소와 재개를 검증했다. C# 231개 검사가 통과했다. 백엔드·웹 코드는 수정하지 않았고 운영 서버에는 요청하지 않았다.

## 7단계 구현: 사용자 지정 경로 최초 수집·보고

`PathReportService`를 기존 POST `/api/where-am-i/v3/path-reports`에 연결했다. 사용자 확인 후 저장된 스크린샷·로그 경로 중 미수집 항목을 보내고, 폴더 직접 선택 시에는 로컬 저장 성공 후 비동기로 보고한다. 자동 탐색 후보는 수집하지 않으며 서버에서 경로를 내려받아 설정을 복원하지 않는다.

전송 필드는 path_type·마스킹한 path·실행 어셈블리의 app_version뿐이다. 현재 프로필 접두사·Windows 사용자 폴더명·이메일 형태를 가린다. 원본 로컬 경로는 그대로 두고 별도 완료 파일에는 종류와 경로 해시만 저장한다. 성공 응답과 완료 상태 저장을 마친 경로는 앱 버전이 바뀌어도 다시 보내지 않는다. 실패 항목은 다음 실행의 사용자 확인 후 다시 시도한다. 상태 파일 손상·저장 실패로 중복이 생기는 것은 서버 정책상 허용한다.

종류별 결과를 분리하고 이전 경로 요청의 늦은 완료가 새 경로를 완료로 표시하지 않도록 한다. 경로 보고는 감지 중지와 독립적으로 수행하고 앱 종료에는 취소한다. 로컬 저장·감시 결과와 수집 결과를 분리한다. 로그 폴더를 드라이브 루트로 지정할 때 끝 구분자를 제거하지 않도록 정규화도 보완했다.

백엔드 소스·기존 API 문서를 읽어 계약을 확인했으나 수정·배포·운영 요청은 하지 않았다. 기존 백엔드 문서의 “시작 시 수집 없음”보다 사용자 확정 방향의 최초 수집·다음 실행 재시도를 우선했다. C# 270개 검사가 통과했으며 운영 DB 저장·Windows 폴더 선택 UI는 별도 확인이 필요하다.

## 8단계 구현: 사용자 확인 후 버전 확인 준비

`AppVersionInfo`로 실제 실행 어셈블리 버전을 읽고 경로 수집과 버전 확인에서 같은 값을 사용한다. 기존 기본값을 유지하는 Version 1.0.0을 프로젝트에 명시했으며 실제 어셈블리는 1.0.0.0이다. 배포 때 빌드 버전을 지정할 수 있다.

`VersionCheckService`와 앱 버전 카드를 추가했다. 사용자 확인 성공 후 한 번 비동기로 확인하고 재확인 버튼을 제공한다. 10초 제한·중복 조회 방지·종료 취소를 적용하며 감지와 독립적으로 동작한다. 업데이트 없음·선택 업데이트·필수 업데이트 안내·확인 실패를 구분하고, 실패를 최신으로 표시하지 않는다. 필수 업데이트에서도 현재 감지를 차단하지 않는다.

서버의 data 객체에서 숫자 버전·현재 버전 에코·최소/최신 관계·업데이트 플래그·다운로드 URL을 검증한다. 사용자 클릭 시 공식 HTTPS 페이지를 브라우저로 열며 자동 다운로드·설치·exe 교체는 하지 않는다. 변경 내용은 일반 텍스트다.

백엔드에는 아직 API가 없어 POST `/api/where-am-i/v3/check-version`을 제안 계약으로 작성했다. [백엔드 API 요구사항](BACKEND_API_REQUIREMENTS.md)에 데이터·버전 규칙·다운로드 호스트·실패/배포 검증을 추가했다. 백엔드·웹 코드와 운영 서버는 변경하지 않았다. C# 321개 검사와 Windows 대상 교차 빌드가 통과했다. 실제 서버 응답과 Windows UI는 별도 검증이 필요하다.

## 9단계 구현: 로그 대상 선택 안정화

`TarkovLogTargetSelector`로 사용자 지정 경로만 탐색하는 정책과 실행 폴더 시각 기반 선택을 분리했다. 설정 저장은 임시 파일 교체를 사용한다. Logs 바로 아래 실행 폴더를 직접 선택해도 부모에서 다음 실행을 찾는다. 과거 파일 수정으로 이전 실행을 선택하지 않으며 최신 대상 삭제 시 기다린다. 경로 변경·앱 재시작 시 선택 기준을 초기화한다. 알 수 없는 폴더명은 최초 발견 시 생성 시각을 사용하고, 인식 가능한 실행 폴더를 우선한다. 링크·정션은 따라가지 않는다.

임시 디렉터리로 경로 정책·신규 실행·삭제·복구·회전·과거 수정·링크 제외를 검사했다. 실제 감시기를 통해 Customs 타이머 복구 → 빈 새 실행으로 상태 초기화 → Woods 타이머 복구를 확인했다. C# 345개 검사가 통과했다. 백엔드 변경은 없으며 PID·실행 여부 판별과 실제 Windows 게임 검증은 별도다.

## 10단계 구현: 맵 별칭 API·로컬 캐시 준비

`MapAliasService`를 추가하여 사용자 확인 후 정상 캐시를 먼저 읽고 별칭 목록을 한 번 조회한다. 새 원격 목록은 전체 검증 후 원자적으로 교체하며, 내장 별칭을 대체값으로 유지한다. 갱신 시 감시기에 재읽기를 요청하여 기존 로그에도 반영한다. API에는 사용자 정보나 경로를 보내지 않는다. 서버 계약은 별도 요구사항 문서에 추가했으며 백엔드·웹 수정이나 운영 요청은 하지 않았다.

응답 크기 256KiB·목록 1024개·10초 제한, 정규화 중복·지원하지 않는 slug 거절, 정상 캐시의 임시 파일 교체를 적용했다. 조회 실패와 손상 목록은 정상 상태를 덮어쓰지 않는다. 저장 실패 시 메모리 적용은 유지하고 활동 이력에 오류를 표시한다. 캐시는 만료시키지 않는다. 원격 목록에서 빠진 별칭은 제거하되 내장 별칭이 있으면 내장값을 사용한다.

가짜 HTTP와 임시 파일로 요청 계약·원격 우선·내장 대체·캐시 복구·잘못된 응답·크기 제한·404·취소·스냅샷 삭제·캐시 손상·저장 실패를 검사했다. 총 C# 365개 검사와 Windows 대상 빌드(경고·오류 0)가 통과했다. 실제 서버·Windows UI 검증은 별도다. 추가 편의 기능은 사용자 확정에 따라 제외하며, 클라이언트는 11~12단계가 남았다.

## 11~12단계 완료: 통합 검사·로컬 Release 패키징

가짜 API와 실제 임시 파일 감시기로 새로운 맵 별칭 조회 → 현재 로그 재분석 → Woods 시작·타이머 복구 → 해시 session_id와 UTC 타이머 전송 → 스크린샷 파일명 좌표 전송을 함께 확인했다. 기존 로그·좌표 전송 계약을 유지한다. 최초 안내 예약 후 즉시 종료하는 경우의 늦은 팝업도 차단했다. README와 사용자 안내에서 제외된 종료·트랜짓·웹 반영 완료 표현을 정리하고 과거 백신 이미지가 이번 빌드 검사 결과가 아님을 명시했다.

C# 373개 검사와 Python 3개 테스트가 통과했다. Release·win-x64·self-contained·single-file publish를 완료했으며 ReadyToRun·trimming은 사용하지 않았다. C# 테스트의 Windows Registry 플랫폼 경고 1개는 macOS 호스트에서 발생하며 제품 Release publish에는 경고가 발생하지 않았다.

`tools/package_release.py`로 `artifacts/where-am-i-1.0.0-win-x64.zip`과 SHA-256·파일별 manifest를 생성했다. 실행 파일·사용 가이드·이미지·변경 내용·Windows 검증표만 포함하고 로그·테스트 샘플·사용자 설정은 포함하지 않았다. ZIP 무결성을 검사했다. 12단계의 로컬 산출물 준비는 완료이며 실제 Windows 실행·UI/DPI·게임·백엔드/웹 검증은 [체크리스트](WINDOWS_VALIDATION.md)에 남겼다. 외부 업로드·공개 배포·코드 서명·백신 검사는 수행하지 않았다.

## 추가 샘플: 오후 Streets 별칭 누락

13:53:59 실행 로그에서 14:48:39.426과 14:55:12.634에 `maps/city_preset.bundle rcid:city.scenespreset.asset`가 기록됐다. 레이드 시작은 각각 14:50:47.341, 14:57:40.138이며 GameTimer 관측 당시 잔여 시간은 두 번 모두 40분이다. 기존 내장 별칭은 tarkovstreets만 포함하고 city가 빠져 맵이 null이 되는 입력을 확인했다. `city → streets-of-tarkov`를 추가했다.

원본에서 scene·GameStarted·GameTimer 행만 정제해 streets-city-repeat 시나리오로 추가했다. 로딩 단계의 API 스냅샷에도 정식 맵이 포함되고 시작·타이머는 아직 null인지 검사한다. DB 별칭은 아래 SQL로 운영자가 추가할 수 있으며 이 작업에서 운영 DB는 변경하지 않았다.

```sql
INSERT INTO where_am_i_map_aliases (alias, map_slug)
VALUES ('city', 'streets-of-tarkov')
ON CONFLICT DO NOTHING;
```
