# 레이드 타이머 전송: 백엔드 API 요구사항

작성일: 2026-10-19. 이번 작업은 **데스크톱 클라이언트 전송 구현과 이 요구사항 문서 작성**까지다. 백엔드·웹 코드는 수정하지 않았고 배포·운영 API 호출도 수행하지 않았다.

## 목적과 역할

클라이언트는 application 로그의 맵·레이드 시작과 output 로그의 GameTimer를 연결하여 전송한다. 좌표는 기존 스크린샷 방식을 유지한다. 서버는 타이머 기준을 사용자 개인 WebSocket으로 전달하고, 웹은 현재 잔여 시간으로 Woods의 BTR 예상 운행·정차 정보를 표시한다. 실제 BTR 도착·정차·출발 이벤트, 정확한 종료 판정, 실제 트랜짓 연결은 요구하지 않는다.

Woods에서 자동 타이머를 우선 검증한다. Customs·Shoreline은 타이머가 없어도 정상 요청으로 처리해야 한다. Woods도 타이머 미확보 시 임의의 35분으로 시작하지 않고 웹 수동 입력을 유지한다. 샘플의 Woods 35분은 검증값이며 서버의 고정 상수가 아니다.

## 확인한 기존 구현과 변경 지점

인접 로컬 백엔드 저장소 `eft-library-back`의 현재 소스를 읽어 확인했다. 운영 배포와 동일한지는 확인하지 않았다.

| 위치 | 현재 동작 | 필요한 변경 |
| --- | --- | --- |
| `api/where_am_i/where_am_i_router.py` | POST `/v3/send-raid-state` → `WhereAmIServiceV3` | 기존 경로 유지 |
| `api/where_am_i/req_models.py` | `RaidStateRequestV3`에 맵·시작·활성·트랜짓만 존재 | 아래 nullable 필드 3개 추가·검증 |
| `api/where_am_i/service.py` | 사용자 확인 후 email을 제외한 모델을 JSON으로 전달 | 타이머 필드가 제외·유실되지 않는지 검증 |
| `util/location_socket_v3.py` | `wpf_raid_state` Redis 발행·개인 WebSocket 전달 | 새 필드 유지, 재접속용 캐시 만료 정책 개선 |
| `api/response.py` | `{status, msg, data}` 응답 | 성공은 `data: true`, 수신·전달 실패는 성공으로 응답하지 않음 |

기존 모델은 추가 필드를 선언하지 않아 클라이언트가 보낸 타이머 값이 무시될 수 있다. 따라서 **구버전 서버의 HTTP 200 + data:true만으로 타이머 지원 여부를 확인할 수 없다.** 새 필드를 실제로 전달하는 백엔드 배포와 WebSocket 검증이 필요하다.

기존 인증·사용자 확인 흐름은 유지한다. `session_id`는 인증 정보가 아니다. 타이머를 PostgreSQL에 새로 저장하거나 별도 BTR 정차 테이블을 만드는 작업은 필요하지 않다. DB 작업이 추가된다면 백엔드의 `platform_db.sql`·V3 규칙을 따라 별도로 설계한다.

## API 계약

`POST /api/where-am-i/v3/send-raid-state`

Content-Type: `application/json`. 개발·운영 기본 주소는 해당 배포 설정을 따른다. 데스크톱의 현재 기본 주소는 `https://back.eftlibrary.com`이다.

| 필드 | 타입·기본값 | 의미 |
| --- | --- | --- |
| `email` | string, 기존 필수값 | 기존 사용자 식별 |
| `map` | string 또는 null | `bigmap`, `city`, `Rezerv_Base`, `woods` 등 로그 원본 맵 이름. 서버에서 정식 맵으로 변환 |
| `started_at` | 시간대 포함 ISO 8601 또는 null | application에서 감지한 시작 시각 |
| `is_active` | boolean, 기존 필수값 | 클라이언트가 시작을 감지했는지. 정확한 종료 판정은 아님 |
| `transit_count` | integer, 기본 0 | 기존 클라이언트 호환 필드. 신규 클라이언트는 0 |
| `session_id` | string 또는 null, 기본 null | **추가**: 실행 폴더 식별값과 로딩 시각을 SHA-256으로 해시한 64자리 소문자 16진수 |
| `timer_observed_at` | 시간대 포함 ISO 8601 또는 null, 기본 null | **추가**: GameTimer의 utcNow, UTC 직렬화 |
| `raid_ends_at` | 시간대 포함 ISO 8601 또는 null, 기본 null | **추가**: GameTimer의 escape, UTC 직렬화 |

새 필드는 모두 선택값으로 추가하여 기존 클라이언트 요청도 계속 받는다. 클라이언트는 타이머가 없을 때 두 시간 필드를 **명시적 null**로 보낸다. 새 클라이언트가 보내는 null은 이전 타이머를 유지하라는 뜻이 아니라 현재 스냅샷에 타이머가 없다는 뜻이다.

`session_id`는 파일 경로 자체를 노출하지 않는다. 같은 실행·같은 로딩 시각에서는 타이머가 늦게 도착하거나 앱을 다시 실행해도 동일하며, 같은 맵 재입장이나 실행 폴더가 바뀌면 달라진다. 맵 전환·로딩 단계에서 시작 시각은 null일 수 있다. 로그가 전혀 없으면 session_id도 null이다.

### Woods 요청 예시

식별자·이메일은 설명용이다. 시간은 실제 Woods 샘플의 값이다.

```json
{
  "email": "player@example.com",
  "map": "woods",
  "started_at": "2026-10-19T08:40:33.493+09:00",
  "is_active": true,
  "transit_count": 0,
  "session_id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "timer_observed_at": "2026-10-18T23:40:32+00:00",
  "raid_ends_at": "2026-10-19T00:15:32+00:00"
}
```

타이머 관측 당시 잔여 시간은 `raid_ends_at - timer_observed_at = 2100초`다. 전송·재접속 이후에도 관측 시점의 35분을 새로 시작하면 안 된다.

### 타이머가 없는 요청

```json
{
  "email": "player@example.com",
  "map": "customs",
  "started_at": "2026-10-19T08:25:21.809+09:00",
  "is_active": true,
  "transit_count": 0,
  "session_id": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "timer_observed_at": null,
  "raid_ends_at": null
}
```

Customs·Shoreline뿐 아니라 Woods에서 타이머를 아직 찾지 못한 경우도 위와 같이 정상 처리한다. 로딩 중에는 `started_at: null`, `is_active: false`, 두 타이머 값 null로 이전 레이드 타이머를 초기화한다. 이 요청을 실제 사망·탈출의 증거로 사용하지 않는다.

## 검증·성공·실패 응답

- 타이머 두 필드는 모두 null이거나 둘 다 유효한 시간이어야 한다. 하나만 있으면 HTTP 422.
- 시간이 있는 경우 시간대 정보가 필수이며 UTC로 정규화한다. `raid_ends_at > timer_observed_at`이어야 한다.
- 타이머가 있는 요청은 `is_active: true`, 확인된 map, started_at과 session_id가 있어야 한다. 시작 전 또는 맵 미확인 타이머를 웹 자동화에 사용하지 않는다.
- 신규 session_id가 있다면 64자리 소문자 16진수를 검증한다. 기존 클라이언트의 생략·null은 허용한다.
- 서버 처리 시 이미 만료된 타이머를 다시 활성화하지 않는다. 타이머 만료 요청은 HTTP 409와 `detail: "RAID_TIMER_EXPIRED"`로 거부하는 방식을 요구한다. 단순히 원본 전체 레이드 길이로 복원하면 안 된다.
- 사용자 확인 실패·Redis 발행 실패는 `data: true`로 응답하지 않는다. 서버 일시 장애는 HTTP 503을 권장한다. 인증·유효성 실패는 해당 4xx로 구분한다.

정상 수신·상태 저장·발행이 완료된 응답은 기존 계약을 유지한다.

```json
{
  "status": 200,
  "msg": "OK",
  "data": true
}
```

클라이언트는 **HTTP 성공 + data:true**만 요청 성공으로 표시한다. `data:false`, `data:null`, 키 누락, 잘못된 JSON은 성공으로 표시하지 않는다. 이 응답은 특정 브라우저의 수신·BTR 화면 반영 완료를 의미하지 않는다.

## WebSocket·캐시·순서 처리

기존 `wpf_raid_state` 이벤트의 payload에 새 필드 3개를 그대로 포함한다. email은 현재처럼 payload에서 제외한다. 기존 이벤트 메타데이터·개인 채널·재연결 동작을 유지한다.

```json
{
  "type": "wpf_raid_state",
  "payload": {
    "map": "woods",
    "started_at": "2026-10-19T08:40:33.493+09:00",
    "is_active": true,
    "transit_count": 0,
    "session_id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "timer_observed_at": "2026-10-18T23:40:32Z",
    "raid_ends_at": "2026-10-19T00:15:32Z"
  }
}
```

- 같은 session_id로 늦게 들어온 유효한 타이머가 웹까지 전달되어야 한다. 맵·started_at이 같다는 이유로 업데이트를 생략하면 안 된다.
- 새로운 session_id 또는 로딩 스냅샷에서 이전 타이머를 비운다. 맵 이름만으로 연결하면 같은 맵 재입장을 구분할 수 없다.
- 같은 스냅샷은 재시도로 중복될 수 있다. 중복 이벤트가 와도 타이머 시작 기준을 현재 시각으로 다시 잡지 않는다.
- 현재 Redis의 레이드 캐시는 고정 60초다. 클라이언트는 변경 시 전송하므로 60초 뒤 새로 연 웹에서 타이머를 복구하지 못한다. 유효 타이머가 있는 상태는 최소 `ceil(raid_ends_at - 서버 현재 시각) + 60초` 동안 보관하는 정책으로 개선한다. 타이머 없는 구버전 상태의 TTL은 기존 정책을 유지할 수 있다.
- 캐시 만료 전이라도 이미 지난 종료 예정 시각을 자동 타이머로 되살리지 않는다.
- 클라이언트 한 인스턴스에서는 요청을 직렬화하고 대기 중인 오래된 스냅샷을 버린다. 서버는 재시도·시간 초과 이후 늦게 완료되는 요청·복수 클라이언트의 이전 상태가 새 상태를 덮어쓰는 정책도 별도로 정해야 한다. session_id 해시값을 정렬하여 시간 순서로 판단하면 안 된다. 현재 payload만으로 모든 로딩 스냅샷의 전역 순서를 보장할 수는 없다.

## 웹 연동 시 지킬 조건

이번에는 웹 코드를 수정하지 않는다. 아래는 후속 연동 요구사항이다.

- 개인 WebSocket의 RaidState 타입·검증에 nullable session_id/timer_observed_at/raid_ends_at을 추가한다. 기존 이벤트의 새 필드 생략도 허용한다.
- 화면의 맵과 이벤트의 맵이 일치하고 활성·타이머 값이 유효한 경우에만 자동 적용한다. Woods 우선 검증 후 다른 맵으로 확장한다.
- 현재 웹의 `BTR_AUTO_TRACKING_ENABLED = false`와 맵 기본 길이 기반 계산을 확인한다. 자동화를 연결할 때는 **로그로 확보한 타이머**를 사용하고, 타이머가 없으면 기존 수동 입력을 유지한다.
- 현재 잔여 시간은 종료 예정 UTC 시각에서 현재 UTC 시각을 빼고 0으로 하한 처리한다. 전송·재연결 지연을 반영하고, 같은 이벤트를 수신할 때마다 처음부터 재시작하지 않는다.
- 브라우저·게임 PC·서버 시계 오차와 로그 행 시각 대비 GameTimer 내부 시각 차이를 실제 게임 화면과 비교한다. 필요한 시계 보정·허용 오차는 검증 결과로 확정한다.
- 새 세션에서는 이전 자동 기준과 이전 세션의 수동 타이머를 정리한다. 사용자가 현재 세션에서 수동 보정한 값의 우선순위와 자동 전환 행동을 명확하게 제공한다.
- 자동 기준이 확보됐는지와 수동 대기/수동 실행 상태를 구분한다. BTR 운행은 기존처럼 예상 정보로 표시한다.

## 클라이언트에 구현한 전송 정책

`SendRaidStateRequest`·`RaidSessionSender`로 구현했고, `SessionChanged`에서 전송한다. 별도 BTR 전용 API는 호출하지 않는다.

- 기존 맵·시작·활성·트랜짓 필드 유지, 새 필드 3개 추가.
- 타이머가 뒤늦게 발견되면 같은 세션으로 다시 전송. 타이머는 맵과 레이드 시작이 모두 확보됐을 때만 포함.
- 네트워크 오류·HTTP 시간 초과·408·429·5xx에 한해 총 3회까지 시도. 재시도 대기는 1초·2초다. 영구 4xx와 논리적 실패(data:true가 아님)는 자동 반복하지 않음.
- 최신 스냅샷만 순차 전송. 과거 응답으로 현재 전송 상태를 덮어쓰지 않음.
- 감지 중지·종료 시 대기·진행 중 요청과 재시도 대기를 취소. 재개 시 같은 상태라도 다시 수집·전송.
- 세 번 모두 실패한 후 무한 재시도하거나 영구 큐에 쌓지 않음. 다음 상태 변경 또는 감지 재개 시 재전송.
- 서버의 타이머 필드 지원 여부와 웹 수신을 별도로 확인해야 함. 기존 서버가 새 필드를 무시해도 data:true를 반환할 수 있음.

## 백엔드 구현 완료 기준

1. 기존 클라이언트 요청과 타이머 없는 세 맵의 요청을 정상 처리한다.
2. Woods 샘플의 관측·종료 시각이 API 모델 → 서비스 → Redis → 개인 WebSocket에서 보존된다.
3. 타이머 지연 추가, 같은 맵 재입장, Customs → Woods, 명시적 null에서 이전 타이머가 섞이지 않는다.
4. 요청 60초 이후 웹을 열거나 재연결해도 아직 유효한 타이머를 복구한다.
5. 부분 시간·시간대 누락·역전된 시간·만료된 타이머·사용자 확인 실패·Redis 실패가 성공 응답으로 처리되지 않는다.
6. 같은 요청의 재시도·WebSocket 재생이 타이머를 처음부터 재시작하지 않는다.
7. 웹 후속 연동 뒤 실제 Woods 게임 잔여 시간과 BTR 예상 표시를 비교한다. 실제 정차 관측 데이터로 소개하지 않는다.

기록된 과거 샘플로 검증할 때는 서버 시각을 샘플 관측 시각에 고정하거나 모든 시간값을 같은 간격만큼 이동한다. 실제 현재 시각으로 과거 요청을 재전송하면 만료 요청으로 거부되는 것이 정상이다.

배포 순서는 백엔드의 새 필드 전달·캐시 검증, 클라이언트 배포, 웹 자동 타이머 적용 검증 순으로 진행한다. 이 문서 작성만으로 서버·웹 구현이나 운영 연동이 완료된 것은 아니다.

## 후속 클라이언트 변경: 스크린샷 전송 안정화

6단계에서 스크린샷에도 공통 응답 검사·최신 대기값 유지·직렬화·총 3회 이내 재시도·취소를 적용했다. 스크린샷은 기존 `/api/where-am-i/send-location`의 email·location만 보내며 이 문서의 타이머 필드를 추가하지 않는다. 네트워크 시간 초과 후 같은 파일명 요청이 재전송될 수 있으므로 서버는 이를 수신 순서·중복 처리 정책에서 고려한다. 클라이언트 취소가 서버에서 이미 완료·진행 중인 저장·발행을 되돌리지는 않는다. 위 레이드 타이머 API 요구사항과 백엔드·웹 미구현 상태는 그대로다.

## 구현된 경로 수집 API와 클라이언트 정책

타이머 API 후속 작업과 별개로 기존 POST `/api/where-am-i/v3/path-reports`는 백엔드 소스에 이미 구현돼 있다. 7단계 클라이언트는 path_type·path·app_version 세 필드와 HTTP 성공 + data:true 계약을 사용한다. 이메일·사용자 ID·collection_source·created_at을 추가하지 않는다. 마스킹은 클라이언트에서 수행하고 원본 로컬 설정은 유지한다.

기존 서버 문서 `docs/where_am_i_path_reports_v3_desktop.ko.md`는 초기 “시작 시 수집·재시도 없음” 정책이지만, 이 대화에서 사용자 확정 방향은 **기존 저장 경로 최초 수집과 실패 항목 다음 실행 재시도**다. 현재 클라이언트는 그 방향을 따른다. 서버의 추가 필드나 새 엔드포인트는 필요하지 않으며 기존 중복 허용 정책을 유지한다. 이 차이는 백엔드 문서의 후속 갱신 대상으로 남긴다. 원본 게임 파일·자동 탐색 후보·이메일을 경로 수집에 추가하지 않는다.

백엔드 코드는 수정하지 않았고 실제 운영 API·DB 저장은 검증하지 않았다. 클라이언트의 완료 파일에는 종류별 경로 해시를 저장하며 서버의 경로 조회 API를 요구하지 않는다.

## 제안: 데스크톱 버전 확인 API — 8단계 클라이언트 준비

**현재 백엔드에는 아래 API·배포 버전 테이블이 없다.** 이번 단계는 클라이언트와 계약 제안만 구현했으며, 서버 코드를 수정하지 않았다. 서버 미배포·404·조회 실패 시 클라이언트는 “버전 확인 실패”로 표시하고 감지를 계속 허용한다.

### 경로와 요청

제안 경로: `POST /api/where-am-i/v3/check-version`.

```json
{
  "product": "where-am-i",
  "current_version": "1.0.0.0",
  "platform": "windows",
  "architecture": "x64",
  "channel": "stable"
}
```

필드는 위 다섯 개이며 이메일·사용자 ID·로컬 경로는 필요하지 않다. 현재 배포 대상은 Windows x64 stable이다. 다른 플랫폼·아키텍처·채널을 지원하려면 서버와 클라이언트 계약을 함께 확장한다. 공개 배포 메타데이터 조회로 설계하고 별도 인증이 필요하면 기존 데스크톱 인증 흐름과 합의한다.

실제 실행 어셈블리의 4자리 숫자 버전을 읽어 전달한다. `.csproj`의 기본 Version은 기존 기본값과 같은 1.0.0이며 현재 어셈블리는 1.0.0.0이다. 빌드 시 `-p:Version=...`으로 실제 배포 번호를 지정해야 한다. .NET SDK가 어셈블리 버전을 생성하며, 클라이언트는 Git 해시·InformationalVersion을 비교값으로 보내지 않는다. 경로 수집의 app_version도 같은 값을 사용한다.

### 응답과 비교 규칙

아래 버전·URL은 설명용이며 실제 공개 배포가 아니다.

```json
{
  "status": 200,
  "msg": "OK",
  "data": {
    "current_version": "1.0.0.0",
    "latest_version": "1.1.0.0",
    "min_supported_version": "1.0.0.0",
    "update_available": true,
    "update_required": false,
    "download_url": "https://github.com/eft-library/eft-library-where-am-i/releases/tag/live-map-v2",
    "release_notes": "변경 내용"
  }
}
```

- `data`는 객체여야 한다. 다른 데스크톱 API의 data:true 응답을 그대로 재사용하지 않는다.
- current_version·latest_version·min_supported_version은 2~4개 숫자 구성, 최대 64자다. 빠진 구성은 0으로 비교한다. 1.0과 1.0.0.0은 같으며 1.10은 1.9보다 크다. SemVer의 사전 배포·+metadata 표기는 이번 stable 계약에서 지원하지 않는다.
- 서버는 요청의 current_version을 그대로 또는 숫자 의미가 같은 값으로 응답한다. 다른 현재 버전에 대한 응답은 클라이언트가 거부한다.
- `update_available`은 current < latest, `update_required`는 current < min_supported여야 한다. min_supported <= latest여야 한다. 문자열 정렬로 비교하지 않는다.
- 현재 버전이 공개 최신보다 높다면 update_available=false, update_required=false로 응답할 수 있다. 클라이언트 문구는 “사용 가능한 업데이트가 없습니다”이며 현재 버전이 공개 최신과 정확히 같다고 단정하지 않는다.
- 업데이트가 있으면 유효한 download_url이 필요하다. 공식 배포는 GitHub를 사용한다. 현재 소스는 HTTPS·기본 443 포트·사용자 정보 없는 `github.com/eft-library/eft-library-where-am-i/releases`와 그 하위 릴리스·asset 주소를 허용한다. 기존 `eftlibrary.com`·`www.eftlibrary.com` 주소는 호환성을 위해 유지한다. 다른 저장소·호스트는 거부한다. 이 변경 전 exe는 GitHub를 거부하므로 백엔드 재배포와 함께 수정된 exe를 다시 빌드·배포해야 한다.
- 업데이트가 없으면 download_url은 null·생략·빈 문자열을 허용한다. 업데이트가 없을 때 다운로드 버튼은 비활성화한다.
- release_notes는 일반 텍스트 최대 4,000자이며 null·생략을 허용한다. HTML·스크립트로 렌더링하지 않는다.
- HTTP 오류, 잘못된 JSON·필드 타입, 모순된 버전/플래그, 지원하지 않는 다운로드 URL은 클라이언트에서 확인 실패로 처리한다. 실패를 “최신”으로 표시하지 않는다.

### 서버 데이터와 구현 범위

신규 V3 모델·서비스·쿼리로 구현하며 기존 API·레거시 코드를 덮어쓰지 않는다. 배포 버전 테이블은 새 마이그레이션으로 추가하고 `platform_db.sql`에도 반영한다. 현재 스키마에 해당 테이블이 없는 상태이므로 이름과 자료형은 백엔드 구현에서 확정한다.

후보 필드는 product·version·platform·architecture·channel·min_supported_version·download_url·release_notes·published_at·is_active이며 기존 feature/design 문서 9.8을 참고한다. 공개된 활성 배포 중 제품·플랫폼·아키텍처·채널에 맞는 최신 버전을 숫자 규칙으로 선정한다. 조회 실패·대상 배포 없음은 404/503 등 실패 응답으로 구분하고 임의 최신 버전을 만들어 반환하지 않는다.

필수 업데이트는 현재 클라이언트에서 안내만 한다. 감지 차단·자동 설치·exe 교체는 구현하지 않는다. 서버가 특정 클라이언트 버전을 지원하지 않을 경우 실제 기능 API의 제한 정책도 별도로 정해야 한다. 버전 조회 실패 때문에 기존 감지·스크린샷·레이드 전송을 차단하지 않는다.

### 클라이언트 동작과 완료 기준

사용자 확인 성공 후 비동기로 한 번 확인하고 “버전 다시 확인”으로 수동 재확인한다. 별도 10초 제한 시간을 적용하며 중복 확인을 막고 종료 시 취소한다. 감지 중지와 버전 확인은 독립이다. 자동 재시도·주기 폴링·업데이트 팝업은 추가하지 않아 반복 알림을 피한다. 현재 버전·확인된 최신/최소 버전·마지막 확인 시도 시각·변경 내용을 표시한다.

다운로드는 사용자가 버튼을 누를 때 승인된 공식 URL을 브라우저로 연다. 자동으로 파일을 내려받거나 실행하지 않는다. 새 확인이 실패하면 이전 링크·최신 정보로 성공을 가장하지 않고 미확인 상태를 표시한다.

백엔드 완료 검증에는 동일 버전·숫자 순서 1.9/1.10·선택/필수 업데이트·현재 버전이 더 높은 경우·버전 조회 실패·아키텍처 불일치·공식 다운로드 링크를 포함한다. 운영 API 배포 후 Windows에서 실제 현재 버전과 응답·브라우저 열기를 확인해야 한다. 클라이언트의 가짜 HTTP 검증만으로 서버·배포 완료로 보지 않는다.

## 맵 별칭 API — 과거 클라이언트 계약 (현재 호출하지 않음)

아래는 이전 단계의 기록이다. 최신 클라이언트는 이 API를 호출하거나 캐시를 사용하지 않는다. 뒤의 원본 전송 확정 계약이 우선한다.

백엔드·DB에는 아직 구현하지 않았다. 클라이언트는 사용자 확인 후 한 번 GET `/api/where-am-i/v3/map-aliases`를 요청한다. 요청 본문·이메일·로컬 경로는 없다. 10초 제한이며 즉시 재시도·주기 조회·ETag는 이번 계약에 포함하지 않는다. 서버의 기존 응답 envelope 안에 아래 data를 반환한다.

```json
{
  "data": {
    "version": "2026-10-19.1",
    "aliases": [
      { "alias": "bigmap", "map": "customs" },
      { "alias": "woods", "map": "woods" }
    ]
  }
}
```

- `version`: 비어 있지 않은 최대 128자 불투명 목록 버전. 숫자 크기·날짜로 비교하지 않는다. 새 응답은 전체 원격 목록 스냅샷이다.
- `aliases`: 활성 별칭만 1~1024개. 응답 본문 최대 256KiB. `alias`는 trim·대소문자 정규화·`_preset` 제거 후 영문 소문자·숫자·공백·밑줄·하이픈 1~128자이며 중복을 허용하지 않는다.
- `map`: 클라이언트가 지원하는 정식 slug. customs, woods, shoreline, factory, interchange, the-lab, the-labyrinth, lighthouse, reserve, streets-of-tarkov, terminal, ground-zero 중 하나다. 새로운 slug 추가는 클라이언트 호환성 변경이 필요하다.
- DB 테이블·외래 키·인증 정책은 백엔드에서 기존 스키마에 맞춰 구현한다. DB 모델을 그대로 노출하지 않고 위 필드로 변환한다.

클라이언트는 목록 전체를 검증한 후 원격 목록을 한 번에 교체한다. 원격 별칭이 내장 별칭보다 우선하며 원격 목록에 없는 내장 별칭은 계속 사용한다. 삭제된 원격 별칭은 다음 스냅샷부터 제거되지만 동일 이름의 내장 별칭이 있으면 내장값으로 돌아간다. 내장 별칭 자체를 비활성화하는 tombstone 기능은 없다.

정상 목록은 `%LocalAppData%/EFTLibrary/where-am-i/map-aliases.json`에 임시 파일 교체로 저장한다. 저장 실패 시 이번 실행에는 적용하고 오류를 표시한다. 시작 시 정상 캐시를 먼저 적용하고, HTTP 실패·404·시간 초과·잘못된 응답에는 현재 목록을 유지한다. 첫 실행에서 캐시도 없으면 내장 별칭을 사용한다. 캐시는 만료시키지 않는다. 갱신 후 현재 실행 로그를 다시 읽어 기존 맵 감지를 갱신한다.

검증: DB 변경 → 새 목록 조회 → 실행 파일 재배포 없이 기존 지원 맵의 신규 별칭 감지, 캐시만으로 재시작, 404·손상 응답 시 정상 목록 보존, 정규화 중복·알 수 없는 slug 거절. 실제 서버 수신·DB·운영 연동은 별도 확인한다.

## 원본 맵 이름 전송 — 최종 확정 계약

클라이언트는 별칭 매핑 여부와 관계없이 `map`에 rcid에서 추출한 원본 이름을 보낸다. 대소문자·밑줄을 보존한다. 번들 fallback은 맵 토큰만 추출한다. 클라이언트의 내장 사전·별칭 API 조회·로컬 캐시를 제거했다. `map`의 요청 의미는 정식 slug가 아니라 로그 맵 토큰이다.

| 요청 map / requested_map | 백엔드 별칭 조회 후 map_slug |
| --- | --- |
| bigmap | customs |
| city | streets-of-tarkov |
| Rezerv_Base | reserve |
| woods | woods |
| 미등록 원본 이름 | null |

`requested_map`은 클라이언트가 보낸 값을 그대로 보존하고, 별칭 정규화는 백엔드에서만 수행한다. 기존 필드·URL은 유지한다. 로딩 단계는 started_at=null, is_active=false, 두 타이머 필드=null로 즉시 전송한다. 이후 레이드 시작·유효 GameTimer가 있으면 원본 이름과 두 UTC 타이머를 함께 전달한다. 로컬의 알려진 지도 목록은 타이머 전송 조건이 아니다.

현재 인접 백엔드 소스는 요청 모델에서 원본 이름과 타이머를 허용한 뒤 서비스에서 별칭 DB로 정식 맵을 찾는다. 정식 맵을 찾지 못한 타이머 요청은 422 RAID_MAP_UNRESOLVED를 반환한다. 원본 수집을 유지하려면 로딩 요청은 정상 수집하고, 이 422의 원본도 analytics에 남길지 또는 타이머를 제외하고 수신할지는 서버 정책으로 결정해야 한다. 이번 클라이언트 작업은 백엔드·운영 DB를 수정하지 않는다.

웹에는 서버가 결정한 정식 맵을 전달하며 지원하는 맵만 이동·타이머에 사용한다. 앱의 현재 맵 링크는 원본 토큰이 유효한 정식 경로이면 직접 열고 그렇지 않으면 /live-map 진입점을 연다. 지도 전환은 웹의 서버 상태 수신으로 처리한다. 기존 map-aliases.json 파일은 더 이상 읽지 않는다.
